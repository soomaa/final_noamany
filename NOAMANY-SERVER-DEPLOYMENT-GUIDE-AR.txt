تعليمات تجهيز ورفع تحديثات Noamany على السيرفر
============================================
الإصدار: 1 — تاريخ المراجعة: 2026-10-07
اسم الملف: NOAMANY-SERVER-DEPLOYMENT-GUIDE-AR.txt

الغرض من الملف
--------------
اقرأ هذا الملف كاملاً قبل تجهيز أي نسخة رفع، سواء من جهاز جديد أو بواسطة شخص أو مساعد جديد. راجع الكود الحالي والسيرفر الفعلي، ولا تعتمد على ذاكرة محادثة سابقة أو اسم آخر ZIP فقط. هذا الملف يوثّق أخطاء حدثت فعلاً ومتطلبات منع تكرارها؛ أوامر كل إصدار يجب أن تأتي من الحزمة التي جرى تجهيزها والتحقق منها لذلك الإصدار.
احتفظ بهذا الملف مع المشروع، وأرفقه عند طلب تجهيز نسخة رفع. أضف نسخة منه إلى الحزم المستقبلية وحدّث قسم «آخر حالة مؤكدة» بعد استلام سجل تثبيت ناجح. لا تعتبر مجرد فك الضغط تثبيتاً ناجحاً.

1) قائمة إلزامية قبل تسليم أي نسخة رفع
-------------------------------------
[ ] تحديد آخر نسخة ثبتت فعلاً من سجل السيرفر، والتغييرات اللاحقة عليه.
[ ] تجميع جميع التعديلات المطلوبة وملفاتها الجديدة وتبعياتها، وإعادة المراجعة بعد آخر تعديل.
[ ] مقارنة مخطط قاعدة البيانات وPrisma Client وملفات التشغيل الحالية مع النسخة المرشحة.
[ ] بناء الواجهة والخلفية من المصدر الحالي، والتحقق من نجاح البناء والاختبارات اللازمة للتغييرات.
[ ] تجربة استيراد التطبيق المجمّع مع Client المتوافق مع السيرفر، وفحص استعلامات القراءة المتأثرة.
[ ] مطابقة صفحات sidebar والصلاحيات ومفاتيح API، واختبار موظف بصلاحية عرض فقط وموظف بلا صلاحية.
[ ] إعداد نسخ احتياطي واسترجاع مجرّبين، وفحوص قبل التغيير وبعده، ومنع تثبيتين متزامنين.
[ ] التحقق من ملف HTML الفعلي الذي يخدم الإدارة ومن جميع ملفات JS/CSS والصور والخطوط التابعة له.
[ ] إخراج ZIP بإصدار واضح، وقائمة ملفات وبصمات SHA-256، وأوامر تثبيت ورجوع خاصة به.
[ ] توضيح ما اختُبر محلياً وما لم يُختبر على السيرفر؛ النجاح النهائي يتطلب سجل السيرفر وفحص الوظائف في المتصفح.

2) معلومات البيئة المسجلة — يجب تأكيدها قبل كل رفع
-------------------------------------------------
الدومين: https://final.noamanycenter.com
جذر التطبيق على السيرفر: /home/noamanycenter/final.noamanycenter.com
الاستضافة: cPanel / Passenger.
Node المستخدم في أوامر الإصلاح: /opt/cpanel/ea-nodejs20/bin
يوجد مسار احتياطي مستخدم في بعض الحزم: /opt/cpanel/ea-nodejs22/bin
إصدار Prisma CLI و@prisma/client المسجل: 5.22.0؛ افحص الإصدارين فعلياً قبل تجهيز الحزمة.
المصدر على الجهاز الذي جرى العمل عليه:
E:\final_projects\asmaa\23-8-2026\noamany-engineer17-9
على جهاز آخر يمكن أن يختلف مسار المصدر؛ المطلوب نسخة كاملة وحديثة من المشروع وملفات lock ومرجع آخر رفع مؤكد، وليس ملفات dist القديمة وحدها.

توزيع الملفات الذي تسبب اختلافه في مشكلة كبيرة سابقاً:
- public/index.html: واجهة الموقع العام عند فتح /.
- public/system.html: واجهة نظام الإدارة عند /login ومسارات الإدارة.
- public/assets: ملفات الواجهة المجمّعة وتبعياتها.
- /api: عنوان API من نفس الدومين؛ لا تستبدله بعنوان localhost داخل نسخة الإنتاج.
- /uploads: الملفات المرفوعة الخاصة بالسيرفر؛ يجب الحفاظ عليها.
- dist: الخلفية المجمّعة. افحص مسار تشغيل Passenger الحقيقي؛ لا تفترض أن رفع TypeScript يحدّث التطبيق الجاري.
- توجد نسخ تشغيل إضافية داخل dist/dist في بعض الرفع السابق. تحقق من وجودها واستخدامها قبل التعديل؛ لا تنشئ بنية تشغيل جديدة بالتخمين.

تنبيه: README-FIRST.md وتعليمات استعادة البيانات على جهاز جديد ليست تعليمات تحديث سيرفر قائم. أوامر migrate/seed واستيراد قاعدة محلية الواردة في تجهيز جهاز جديد لا تُنسخ تلقائياً إلى الإنتاج.

3) تجميع التعديلات والبناء من أي جهاز
------------------------------------
أ) اجمع التعديلات مقارنة بمرجع آخر تثبيت ناجح: المصدر، الملفات الجديدة، DTOs، services، controllers، routes، sidebar، الصلاحيات، الترجمة، CSS، الصور والخطوط والإعدادات وملفات lock اللازمة. لا تعتمد على تاريخ تعديل الملف وحده أو الملفات التي كانت موجودة في ZIP قديم.
ب) راجع تعديلاته كاملة، بما فيها تحويلات الاشتراكات والمستردات واللوكر والبحث والباركود إذا كانت ضمن النطاق المطلوب. وجود تعديل في صفحة محلية لا يثبت دخوله في بناء الرفع.
ج) شغّل أوامر البناء المعتمدة في package.json لكل جزء تغير. أعد بناء الأجزاء المتأثرة بعد آخر تعديل؛ إذا تغير المصدر أثناء البناء أو التحزيم، أعد جمعه وبناءه والتحقق منه.
د) ارفع ناتج البناء وتبعياته كاملة. ملف backend جديد قد يحتاج DTO أو service جديداً في dist، وملف HTML جديد يحتاج كل chunks وJS/CSS والصور والخطوط التي يستوردها.
هـ) احسب بصمات المصدر والمدخلات والنواتج، وقارن ملفات ZIP بالنواتج التي اجتازت التحقق. لا تعِد استخدام build قديم بسبب وجوده في المجلد.
و) ثبّت تبعيات البناء وفق lock في بيئة التجهيز، دون نسخ node_modules الخاص بويندوز إلى سيرفر Linux. أي تغيير تبعيات تشغيل على السيرفر يحتاج خطة مستقلة متوافقة مع إصداراته الحالية.
ز) لا تشغّل سكربت assemble-unified-public.js مباشرة على مجلد public الحي؛ السكربت المحلي يعيد إنشاء المجلد ويحذف محتوياته قبل التجميع. احتفظ بملفات assets القديمة على السيرفر لصفحات العملاء المفتوحة والرجوع.

4) أخطاء Prisma السابقة وكيف تُمنع
---------------------------------
4.1 Unknown field / Unknown argument
ظهر عند lines في القيود المحاسبية، items في جرد اللوكر، وعلاقات اشتراكات البرايفت والكافيه.
السبب: الكود يستعمل أسماء علاقات لا يعرّفها Client الجاري، أو مخطط مولّد من قاعدة البيانات أعاد تسميتها.
الإجراء: راجع كل استعلام متأثر مقابل schema وClient الفعليين وعلاقات الجداول. حافظ على أسماء الجداول والأعمدة الفعلية باستخدام @map / @@map عند الحاجة. اختبر include/select والإنشاء المتداخل؛ prisma validate وحده لا يثبت توافق الكود الجاري.

4.2 P1012 / Ambiguous relation
حدث بعد وجود acc_journal_entry_lines وlines كعلاقتين غير مسماتين لنفس الموديل.
الإجراء: صحّح العلاقة المطلوبة دون تكرارها بالخطأ، أو سمِّ العلاقات المختلفة فعلاً مع الطرف المقابل. لا تضف aliases بعشوائية أو sed عام ثم تفترض صحتها.

4.3 Argument id / user_id is missing
ظهر في الحضور وإنشاء المستخدمين وغيرها بسبب غياب default في تعريف Client.
الإجراء: افحص AUTO_INCREMENT الحقيقي في قاعدة البيانات قبل إضافة @default(autoincrement()). لا تولّد أرقاماً يدوياً أو تستخدم MAX(id)+1. راجع @updatedAt والحقول المطلوبة والقيم الافتراضية وفق عقد التطبيق والقاعدة الفعلي.

4.4 Expected String or Null, provided Object
ظهر في rbac_audit_log.detail أثناء حفظ استثناءات المستخدمين.
الإجراء: راجع نوع العمود ومحتواه والكود الذي يكتب ويقرأ الحقل. استخدم Json? عندما تكون القاعدة والعقد متوافقين، أو صحّح التسلسل إلى String حسب الحالة. لا تغيّر كل حقل String إلى Json لمجرد ظهور Object.

4.5 اختفاء enum exports بعد prisma generate
تسبب في Cannot convert undefined or null to object وفشل استيراد التطبيق. كان السيرفر يحتاج 19 اسم enum للتوافق، منها YesNo وBrCode وClubFitnessClassStatus.
الإجراء: إذا لم يتغير المخطط، احتفظ بـClient الحالي ولا تعِد توليده. إذا وجب التوليد، ولّد Client مرشحاً منفصلاً بإصدار السيرفر ومحركات Linux المتوافقة، وأعد aliases التوافق التي جرى التحقق منها دون تغيير native enums أو datamodel. افحص جميع imports الفعلية للتطبيق قبل الاستبدال. تشغيل generate منفرداً يمحو ترقيعات التوافق وقد يعطّل التطبيق. توجد كذلك تهيئة 25 اسم enum داخل bootstrap الحالي قبل استيراد AppModule؛ هذه تهيئة إضافية مختلفة عن 19 export للتوافق داخل Client، ويجب الحفاظ على الاثنين ما دام التطبيق يحتاجهما.

4.6 اختلاف SHA-256 للمخطط أو bootstrap
توقف r6 بسبب اختلاف schema، وتوقفت نسخة 7 أكتوبر بسبب اختلاف dist/main.js.
الإجراء: اجمع الملف الحالي وافحص الفرق أولاً. لا تغيّر expected_source أو manifest إلى البصمة الجديدة لتجاوز الفحص دون مراجعة المحتوى. لا تستبدل schema السيرفر بالمخطط المحلي عمياناً؛ إصلاحات الإنتاج قد لا تكون موجودة في النسخة المحلية. إن احتجت introspection فاعمله في نسخة مؤقتة، وليس db pull فوق مخطط التشغيل الحي.

أرقام مثل 355 autoincrement و148 updatedAt و404 علاقة كانت نتائج مراجعة سابقة، وليست ثوابت لكل إصدار مستقبلي. احسب المتوقع لكل حزمة وراجع الفرق المقصود.

5) أخطاء الواجهة والتوجيه السابقة
--------------------------------
حصل أن الملفات الجديدة رُفعت والبصمات نجحت وAPI كان سليماً، لكن التعديلات لم تظهر: البحث، بطاقات الأعضاء، عرض بيانات المسح تلقائياً، اللوكر، التحويلات والمستردات.
السبب المؤكد: HTML الإدارة الجديد وُضع في public/index.html بينما التطبيق كان يخدم public/system.html القديم. كذلك تغيرت الصفحة العامة / إلى واجهة الإدارة بالخطأ.

متطلبات منع التكرار:
- حافظ على public/index.html للموقع العام، وضع مدخل الإدارة في public/system.html وفق bootstrap الجاري.
- ثبّت assets أولاً ثم مدخل الإدارة في النهاية، مع استبدال الملفات بطريقة آمنة وفحص البصمات.
- لا تحذف public كاملاً ولا تزيل hashed assets القديمة أثناء تحديث عادي.
- بعد التثبيت اجلب HTML من الدومين نفسه مع منع الكاش، وقارن محتواه وبصمته بمدخل الإدارة المرشح، ثم اجلب ملفات JS/CSS المرتبطة وتحقق من وجودها وبصماتها.
- افحص / و/login وروابط الإدارة المباشرة مثل /club/subscriptions و/club/members/barcode-management و/club/lockers/inventory والمسار الجديد في الإصدار.
- تحقق من أن / ما زال يعرض الموقع العام. HTTP 200 قد يكون صفحة HTML خاطئة بدلاً من الملف المطلوب.
- Ctrl+Shift+R خطوة تنظيف كاش بعد التحقق، وليس علاجاً لرفع HTML في المكان الخطأ.

6) صلاحيات sidebar وAPI والبيانات الخاصة بالموظف
-----------------------------------------------
أ) اجعل أسماء الإدارات والصفحات وترتيبها في مصفوفة الصلاحيات مطابقاً لمصدر sidebar الحالي، بما فيها الصفحات الفرعية والجديدة. تحديث catalog وحده لا يضيف رابطاً مفقوداً في الواجهة.
ب) حافظ على مفاتيح الموارد وIDs القائمة وروابط الأدوار والاستثناءات. حدث تعارض /inventory/price-list مع gym-sales.inventory.price_list؛ يُحل بمراجعة ملكية المسار وربطه الصحيح، لا بحذف المورد وإنشائه من جديد وفقد الصلاحيات المرتبطة به.
ج) طابق لكل صفحة جميع طلبات API وطلبات الخيارات والبحث والتصدير والطباعة مع controller/action/resource الفعلي. التقفيل اليومي ظهر لموظف بصلاحية صفحة ثم رد API بـ403 بسبب اختلاف مفاتيح الحماية.
د) اختبر الحماية الفعلية: الموظف المسموح يقرأ البيانات المطلوبة، وغير المسموح يُرفض، والعرض وحده لا يسمح بإضافة أو تعديل أو حذف. حافظ على الرفض الصريح وحدود الفرع والقسم/النوع حسب السياسة المعتمدة. لا تحل 403 بفتح كل APIs أو إعطاء كل الموظفين كل الصلاحيات.
هـ) تزامن catalog يتم داخل معاملة مع حفظ حالته السابقة. الصفحات الجديدة لا تُمنح تلقائياً لكل الموظفين. تحقق من استمرار الأدوار والصلاحيات والاستثناءات الأصلية.

البحث وبطاقات العضوية:
- رد 200 مع [] قد يكون بسبب فلتر خاطئ، وليس خطأ Prisma أو غياب العضو. قارن branch والقسم وURL والفلتر الفعلي بين الموظف والمدير.
- بحث اختيار العضو لعملية اشتراك يستخدم club-members/membership-operation-lookup وفق التنفيذ المعتمد؛ لا تقيده بفلتر «مسجل اليوم» أو منشئ العضو إذا كانت العملية تتطلب العثور على الأعضاء القدامى المسموحين.
- البطاقات تستخدم club-members/print-cards وفق التنفيذ المعتمد لعرض أعضاء نطاق الفرع المسموح. لا تلغِ حدود الفرع للحصول على نتائج.
- لا تنسخ معالجة منتقي الأعضاء إلى قائمة الاستقبال إذا كان لها فلتر يومي مطلوب؛ لكل شاشة عقدها.
- عرض بيانات العضو تلقائياً بعد المسح/كتابة الكود عملية قراءة. تأكد من دخولها في build ومن عدم تحولها إلى تسجيل حضور أو حفظ تلقائي دون الإجراء المطلوب.
- ميّز بين 401 جلسة/تحديث دخول، 403 صلاحية، 404 ملف مفقود، 200[] نتائج فارغة، و500 خطأ تطبيق. اقرأ الرد كاملاً قبل تحديد السبب.

7) ما يجب أن تحتويه حزمة الرفع
------------------------------
- مجلد باسم إصدار فريد وتاريخ ورقم مراجعة؛ لا تعدّل ZIP مسلّماً في مكانه ثم تستخدم نفس الاسم لإصدار مختلف.
- install.sh وrollback.sh خاصان بالحزمة، وREADME بالأوامر الدقيقة، وCHANGELOG وVERIFICATION.
- manifest يحدد الملفات والمسارات والبصمات، baseline المقبول، الملفات المحمية، التغييرات المطلوبة، والتبعيات والإصدارات.
- payload للنواتج اللازمة كاملة، وsource للتغييرات للمراجعة عند الحاجة.
- فحوص صحة وHTML المُقدَّم فعلياً وClient وcatalog والاستعلامات المطلوبة بحسب نطاق الإصدار.
- توضيح ما إذا كانت الحزمة تغير قاعدة البيانات أو schema أو Client أو الصلاحيات، وما هي حدود الرجوع.

لا تضع في ZIP نشر الكود: .env، كلمات المرور، المفاتيح، tokens، نسخة بيانات العملاء، logs حساسة، uploads الإنتاج أو node_modules الخاص بالجهاز. إذا كان نقل بيانات أو مرفقات مطلوباً، تكون له خطة منفصلة ومصرح بها. لا تشارك رسائل DBG التي تحتوي بيانات شخصية أو password hashes دون حجبها.

8) ترتيب التثبيت المطلوب
-----------------------
1. تحقق من جذر التطبيق وإصداراته ومساحة القرص وصحته، وأن لا يوجد تثبيت آخر أو restart سابق معلق.
2. افحص سلامة الحزمة وبصمات baseline؛ اختلاف غير معروف يوقف العملية قبل تغيير التشغيل.
3. جهز الملفات في staging منفصل، وافحص الاستيراد الفعلي للتطبيق المجمّع والاستعلامات والواجهة والصلاحيات المطلوبة.
4. أنشئ backup فريداً ببيان ملفات وبصمات، واختبر سلامته قبل الكتابة. يشمل كل ملف سيُستبدل؛ وإن تغير Client يشمل Client المولّد والترقيعات الخاصة به.
5. نفذ تغييرات metadata الضرورية مع سجل رجوع، ثم ملفات التشغيل؛ assets قبل HTML. تحقق من البصمات بعد الكتابة.
6. اطلب Passenger restart بلمس tmp/restart.txt داخل جذر التطبيق الصحيح.
7. انتظر استهلاك طلب restart، ثم ثلاث استجابات صحة حديثة متتالية، وفحص HTML والأصول والوظائف الجديدة.
8. اطبع حالة نجاح أو فشل واضحة ومسار backup وأمر Undo المطابق له. احتفظ بسجل التثبيت.

المثبّت يجب أن يحاول الاسترجاع عند الفشل بعد بدء التغيير، وأن يفحص صحة التطبيق وHTML القديم بعده. لا يعتبر الرجوع مؤكداً إلا بعد نجاح فحوصه. انقطاع الجهاز/SSH أو توقف الخدمة أو تلف القرص قد يمنع اكتمال الاسترجاع؛ لا تعد بضمان مطلق أن السيرفر لن يتوقف.

ممنوع كإجراء تحديث عام:
- prisma migrate reset / db push --force-reset / --accept-data-loss أو حذف/truncate جداول.
- seed أو استيراد قاعدة محلية قديمة فوق قاعدة الإنتاج.
- تشغيل migrations معلقة كثيرة دون مراجعة كل واحدة وحاجة هذا الإصدار إليها.
- npm install latest أو ترقية Prisma استجابة لإعلان CLI؛ لا ترقي الإصدارات ضمن إصلاح غير متعلق بها.
- prisma generate على Client الحي دون خطة التوافق والفحص المذكورة.
- قتل عمليات Node كلها أو تغيير Passenger إلى PM2/systemd بالتخمين.
- حذف lock تثبيت لمجرد وجوده دون التحقق من عدم وجود عملية جارية.

إذا احتاج الإصدار DDL، افحص بنية القاعدة الفعلية والبيانات أولاً، وحدد تغييرات الإصدار فقط وخطة الرجوع. بعض DDL في MySQL لا يرجع بمجرد rollback معاملة؛ لا تعتمد على ذلك. قد يلزم إبقاء أعمدة جديدة nullable أو سجلات جديدة بعد رجوع الكود لحماية العمل الذي تم بعد التحديث.

10) النسخ الاحتياطي والرجوع
--------------------------
يجب أن يعطي كل تثبيت مسار backup فريداً وأمر Undo كاملاً باستخدام rollback.sh من نفس الإصدار وذلك المسار بالضبط. احتفظ بهما خارج جلسة Terminal.
لا تختَر backup بالاسم «الأحدث» أو wildcard، ولا تستخدم نسخة إصدار آخر، ولا تسترجع dump قديم يمحو اشتراكات وحضور ومدفوعات تمت بعد الرفع.
تحقق من بصمات النسخ وسلامة المسارات ووجودها داخل الجذر المقصود. يرفض الرجوع الكتابة فوق تغييرات أحدث غير معروفة أو backup تالف، ويطبع السبب.
بعد الرجوع: restart بالطريقة الصحيحة، فحوص صحة حديثة، HTML القديم الصحيح وأصوله، واختبار حساب موظف والوظيفة المتأثرة.
الرجوع يعيد ملفات التشغيل وmetadata التي تديرها الحزمة وفق خطتها، ولا يعني محو معاملات العمل الجديدة أو العودة الحرفية لكل بيانات القاعدة إلى وقت سابق. احتفظ بالملفات والأصول التي يحتاجها العملاء المفتوحون والسجلات الجديدة.
عند الفشل قبل أي تغيير للتشغيل لا تسترجع backup قديم بلا داعٍ؛ حل فشل preflight أولاً. عند 500 بعد حفظ عملية، تحقق هل السجل حُفظ قبل تكرار المحاولة لتجنب التكرار إذا فشل audit أو قيد لاحق.
