# تقرير اختبار API التطبيق والحضور والانصراف

تاريخ التنفيذ: 17 أغسطس 2026  
بيئة الاختبار: Backend مبني من آخر source على منفذ اختبار مستقل وقاعدة البيانات المحلية الحالية.

## النتيجة

- إجمالي سيناريوهات HTTP المنفذة: **113**.
- الناجح: **113**.
- الفاشل: **0**.
- بيانات الاختبار: موظفان وحسابان وموقع ووردية وسجلات مؤقتة، وتم حذفها بعد الاختبار.
- لم تُطبع كلمات المرور أو JWT في التقرير أو مخرجات الاختبار.

## اكتمال ملف Postman للتطبيق

تمت مقارنة `NOAMANY_FLUTTER_COMPLETE.postman_collection.json` آليًا مع
Controllers الفعلية في Backend، وليس مع قائمة مكتوبة يدويًا فقط:

- مسارات التوافق مع التطبيق القديم `/Api/*`: **92 من 92** موجودة.
- مسارات التطبيق الحديثة `/api/mobile/*`: **32 من 32** موجودة.
- مسارات رفع الملفات التي يحتاجها التطبيق: **4 من 4** موجودة.
- مسارات ناقصة من Postman: **0**.
- مسارات موجودة في Postman وغير مدعومة بالسيرفر: **0**.

إجمالي Collection هو 168 request لأن بعض المسارات لها سيناريوهات أو طرق استخدام متعددة، بالإضافة إلى واجهات إدارة الحضور التي يحتاجها فريق النظام.

## الحضور والانصراف

تم اختبار السيناريوهات التالية فعلياً:

- تسجيل حضور من تطبيق الموظف داخل النطاق الجغرافي.
- تسجيل انصراف لنفس سجل الحضور.
- رفض إحداثيات غير صالحة.
- رفض البصمة خارج نطاق الفرع.
- التأكد أن تحديد النطاق والفرع المسجلين في البصمة يعتمد على `employees.emp_sign` وليس `employees.branch_id_fk`.
- اختبار مكان بصمة محدد حتى عندما يختلف عن فرع الموظف الإداري.
- اختبار `emp_sign = "all"` واختيار أقرب فرع يحتوي الإحداثيات داخل نطاقه.
- منع تكرار البصمة خلال 45 ثانية.
- منع تكرار الانصراف بعد تسجيله.
- الحضور والانصراف اليدويان مع صلاحيات الفرع.
- إنشاء وردية وتعديلها وحذفها.
- إنشاء شيفت إضافي وعرضه وحذفه.
- إنشاء ساعات إضافية وعرضها وحذفها.
- تقارير البصمة، كشف الحضور الكامل، التأخير، الغياب، الإضافي، وتبديل الشيفت.
- لوحة الحضور وخيارات التسجيل اليدوي.
- إعدادات قنوات التسجيل وقواعد الحضور.
- إضافة جهاز بصمة وحذفه.
- التأكد من أن محاولة مزامنة جهاز غير متصل تعيد خطأ عمل واضحاً بدلاً من نجاح وهمي.
- استيراد ملف XLSX ببنية الأعمدة العشرة المطلوبة.
- مسارات التطبيق القديم: `attendance_new`, `Report_Basma`, `Basma_Today`, `sheft_types`, `dwam_types`, `Report_hours_edafi`, `report_tabdel_sheft`.

## بقية API التطبيق

تم اختبار تسجيل الدخول الحديث والقديم برقم هاتف الموظف وكلمة المرور الافتراضية `102030`، ورفض كلمة المرور الخطأ والطلب بدون token، والملف الشخصي، وdevice token، والإشعارات، والإجازات، والأذونات، والمهام، والتعاميم، والإنذارات، واللوائح، والزيارات، ورفع الصور، والأنشطة، ودليل الموظفين، والرسائل الداخلية، والسلف. كما تم تشغيل مسارات القراءة القديمة المتوافقة تحت `/Api/*` للموديولات المثبتة في التطبيق.

شُغلت أيضاً 19 حالة Jest مركزة لتأكيد إنشاء حساب الموظف باسم مستخدم يساوي رقم الهاتف، وقبول `102030`، وعدم إجبار الموظف على تغييرها، وعقد الدخول الحديث والقديم، وربط البصمة بمكان البصمة. النتيجة: **19 ناجح، 0 فاشل**.

تم اختبار عمليات الإضافة والعرض والتفاصيل والقراءة والحذف/الإلغاء حيث تنطبق، مع التأكد أن السلفة والإجازة والإذن تبدأ كطلبات انتظار.

## العطل الذي تم اكتشافه وإصلاحه

كان إنشاء الإجازة يفسر `users.emp_code` دائماً كأنه `employees.emp_code`. في قاعدة النظام الجديد هذا الحقل يحمل `employees.id`، ولذلك كان يمكن أن تُنشأ الإجازة لموظف آخر عند تطابق رقم عشوائي. تم تعديل الربط ليبحث أولاً بالمفتاح الأساسي `employees.id` ثم يستخدم كود الموظف فقط كـfallback للبيانات القديمة. بعد الإصلاح نجح إنشاء الإجازة ثم قراءتها وإلغاؤها من مسار التطبيق القديم.

## إعادة التشغيل

بعد تشغيل backend:

```powershell
cd backend
$env:TEST_API_BASE_URL='http://127.0.0.1:4000'
npm.cmd run test:mobile-api
```

الاختبار ينشئ fixture مؤقتاً، ينفذ السيناريوهات، ثم ينظف بياناته وملفاته حتى عند حدوث خطأ.

مزامنة جهاز بصمة حقيقي تحتاج IP فعلياً متاحاً على الشبكة. الاختبار الآلي يتحقق من معالجة الجهاز غير المتاح؛ أما إثبات الاتصال بجهاز hardware نفسه فيتطلب عنوان الجهاز ووجوده على نفس الشبكة.
