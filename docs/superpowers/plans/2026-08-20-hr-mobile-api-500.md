# HR Mobile API 500 Errors Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Eliminate unexpected 500 responses from the Flutter HR flows for leave, permission, loan, attendance, and report searches while preserving the legacy `/Api/*` contract.

**Architecture:** Keep the existing legacy controller as the compatibility boundary. Normalize legacy form values there, pass typed values to the existing domain services, and translate known input/data problems into the legacy `{status,message,data}` response instead of leaking server errors. Exercise the real HTTP application and local database with temporary fixtures, then clean all test records.

**Tech Stack:** NestJS 11, TypeScript, Prisma 5, Jest 30, MySQL, Node.js integration scripts.

**Spec:** User report and screenshots supplied on 2026-08-20 for `/Api/Add_Agaza`, `/Api/Add_Ezn`, `/Api/Add_Solfa`, attendance punch routes, and attendance report search routes.

## Global Constraints

- Accept `application/x-www-form-urlencoded` legacy Flutter requests.
- Never trust a posted employee id; use the authenticated JWT employee.
- Keep the legacy response envelope and return validation/business failures without HTTP 500.
- Accept the exact field names shown in the Flutter payloads, including `khsm_form_date_m`.
- Preserve existing modern `/api/mobile/*` behavior.
