# تصميم مزامنة بصمة الحضور المؤجلة

**الهدف:** تمكين تطبيق Flutter من حفظ البصمة محليًا عند انقطاع الإنترنت أو تعذر استجابة الخادم، ثم مزامنتها لاحقًا مع الاحتفاظ بوقت الالتقاط الأصلي بصورة قابلة للتدقيق ومنع التكرار.

## النطاق

يضاف endpoint جديد فقط إلى واجهة الموبايل: `POST /api/mobile/attendance/offline-sync`.

لا يتغير endpoint المباشر `POST /api/mobile/attendance/punch`: يبقى معتمدًا على وقت وصول الطلب. المزامنة المؤجلة هي المسار الوحيد الذي يسمح بوقت التقاط من الهاتف.

## عقد الطلب

بعد رفع الصورة — إن وجدت — إلى `POST /api/uploads/app`، يرسل Flutter:

```json
{
  "offlineId": "UUID-v4 يولده التطبيق مرة واحدة",
  "capturedAtUtc": "2026-08-23T07:14:12.000Z",
  "timezone": "Africa/Cairo",
  "lat": "24.7136",
  "long": "46.6753",
  "photo": "mobile_app/app-20260823abcd.jpg"
}
```

- `offlineId`: فريد لكل مستخدم ولكل محاولة بصمة؛ يعاد استخدامه في كل retry لنفس البصمة.
- `capturedAtUtc`: ISO-8601 شامل المنطقة الزمنية UTC.
- `timezone`: IANA timezone التقطها الجهاز، للاحتفاظ بالسياق وللتدقيق.
- `lat`, `long`, `photo`: نفس عقد البصمة المباشرة.

## قواعد القبول

1. يجب أن يكون `capturedAtUtc` وقتًا صحيحًا، غير مستقبلي، ولا يتجاوز 24 ساعة قبل وقت وصول الخادم.
2. يتحقق الخادم من الموقع والنطاق الجغرافي والموظف والفرع وإعدادات قناة الحضور كما في البصمة المباشرة.
3. يسجل الخادم الوقت الفعلي الذي وصل فيه الطلب (`receivedAtServer`) والوقت الذي صرح به الجهاز (`capturedAtDevice`) منفصلين.
4. يستخدم الخادم وقت الالتقاط — بعد تحويله إلى timezone المرسلة — لتحديد اليوم والشفت واتجاه العملية وحساب التأخير/الخروج المبكر والساعات الإضافية.
5. لا يسمح بإعادة التسجيل: القيمة الفريدة هي `(userId, offlineId)`. retry لنفس القيمة يعيد نفس النتيجة السابقة بدل إنشاء سجل جديد.
6. لا يقبل client timestamp كبصمة موثوقة وحده: تحفظ العملية بعلامة `source=offline_app` و`requiresReview=true` كي يمكن للإدارة مراجعتها.

## البيانات المخزنة

يضاف إلى سجل الحضور الرئيسي وسجل تاريخ الحضور عند توفر الحقول المناسبة:

- `offline_id`
- `captured_at_device` (UTC ISO)
- `captured_timezone`
- `received_at_server` (UTC ISO)
- `sync_source = offline_app`
- `requires_review = 1`

تضاف uniqueness على `(user_id, offline_id)` في سجل مزامنة مستقل، لأن سجل الحضور الرئيسي لا يحتفظ دائمًا بـ user ID لكل عملية.

## الاستجابة

```json
{
  "id": 700,
  "type": "in",
  "lateMin": 5,
  "branchId": 3,
  "branchName": "اسم الفرع",
  "distanceMeters": 72,
  "offlineId": "UUID-v4",
  "capturedAtDevice": "2026-08-23T07:14:12.000Z",
  "receivedAtServer": "2026-08-23T09:15:04.000Z",
  "requiresReview": true,
  "replayed": false
}
```

إذا أعيد الطلب نفسه بعد أن سجل بنجاح: يعاد نفس الرد مع `replayed: true`.

## أخطاء العميل

- `400`: وقت غير صالح، وقت مستقبلي، تجاوز حد 24 ساعة، خارج نطاق الشفت أو الموقع، أو بصمة مكررة غير متوافقة.
- `401`: token غير صالح.
- `403`: الحساب ليس موظفًا صالحًا.
- `409`: `offlineId` مستخدم سابقًا ببيانات تختلف عن البصمة الأصلية.

## تدفق Flutter

1. يلتقط التطبيق الموقع والصورة ووقت الجهاز في UTC وينشئ UUID واحدًا.
2. عند عدم الاتصال يحفظ العنصر في قاعدة محلية مشفرة بحالة `pending`.
3. عند عودة الاتصال يرفع الصورة أولًا، ثم يرسل عنصر المزامنة.
4. لا يغير `offlineId` أو `capturedAtUtc` عند retry.
5. عند timeout بعد الإرسال يعيد نفس الـ request بنفس `offlineId`؛ الرد replay-safe.
6. عند `400/401/403/409` يوقف retry التلقائي ويعرض حالة تحتاج تدخلًا.

## الاختبارات المطلوبة

- قبول بصمة مؤجلة داخل 24 ساعة وتسجيل وقت الالتقاط والوصول.
- رفض بصمة أقدم من 24 ساعة أو مستقبلية.
- إعادة نفس `offlineId` تعيد النتيجة نفسها دون صف حضور ثانٍ.
- إعادة `offlineId` نفسه مع بيانات مختلفة تعيد `409`.
- استخدام وقت الالتقاط في احتساب دخول/خروج الشفت والتأخير.
- تطبيق فحص النطاق الجغرافي على البصمة المؤجلة.
