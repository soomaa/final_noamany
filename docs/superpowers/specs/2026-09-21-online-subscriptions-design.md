# تصميم: طلبات اشتراك الموقع وربط باقات الموقع بالنظام

**الحالة:** بانتظار مراجعة واعتماد صاحب المشروع قبل التنفيذ  
**النطاق:** موقع العضوية العام، لوحة الإدارة، وخدمة الاشتراكات الخلفية.

## الهدف

تحويل زر «اطلب السعر» إلى «اشترك الآن»، وعرض باقات الموقع التي يختارها مدير البوابة من أنواع الاشتراكات الحقيقية في النظام. يستطيع العضو إرسال طلب اشتراك يدوي مع طريقة الدفع النشطة وصورة إثبات الدفع. يراجع الموظف الطلب في شاشة «اشتراكات الأونلاين» ثم يقبله أو يرفضه. القبول ينشئ اشتراكاً حقيقياً في النظام ويرسل إشعاراً للعضو؛ الرفض يحفظ السبب ويرسل إشعاراً به.

هذه الميزة **ليست بوابة دفع إلكترونية**؛ الدفع يتم خارج الموقع وإثباته هو صورة يرفعها العميل.

## قواعد الربط بين باقة الموقع ونوع الاشتراك

1. في شاشة «باقات عضوية الموقع» يضاف حقل إلزامي: **نوع الاشتراك من النظام**.
2. الحقل يكون قائمة اختيار، لا إدخالاً يدوياً، وتعرض فقط أنواع الاشتراكات التي حالتها نشطة ومفعلة لكل الفروع (`is_active = true` و`apply_to_all_branches = true`).
3. تحفظ باقة الموقع `subscriptionTypeId` في قاعدة البيانات. الاسم والسعر والمدة على الموقع تأتي من نوع الاشتراك المرتبط، لا من حقول تسويقية قابلة للتعارض.
4. تبقى حقول العنوان والوصف والمزايا والترتيب و«الأكثر اختياراً» خاصة بعرض الموقع. عند اختيار النوع، يعرض النموذج اسم الباقة والسعر والمدة للقراءة فقط حتى يعرف المدير ما الذي ربطه.
5. لا تظهر باقة للعامة إن كان الرابط مفقوداً، أو إن أوقف نوع الاشتراك لاحقاً، أو لم يعد متاحاً لكل الفروع. لا يوجد fallback لباقات HTML ثابتة غير مرتبطة بالنظام.

## نموذج البيانات والترحيلات

### باقات الموقع

يضاف عمود nullable باسم `subscription_type_id` إلى `portal_content_items` مع فهرس ومفتاح خارجي إلى `club_subscription_types.id`. يستخدم هذا العمود فقط عندما يكون `content_type = 'membership-plans'`.

### طلب الاشتراك الإلكتروني

يضاف جدول `online_subscription_requests` يحتوي على الأقل على:

| الحقل | الغرض |
| --- | --- |
| `id` | رقم الطلب |
| `status` | `pending` أو `approved` أو `rejected` |
| `member_id`, `member_code`, `customer_name`, `branch_id` | هوية العميل ولقطة منها وقت الطلب |
| `subscription_type_id`, `subscription_type_name`, `subscription_value`, `duration_days` | الباقة والقيمة والمدة كنسخة ثابتة للمراجعة |
| `requested_start_date`, `requested_end_date` | تاريخ البداية المختار والنهاية المحسوبة وقت الطلب |
| `payment_method_id`, `payment_method_name`, `payment_base_method` | طريقة الدفع النشطة المختارة ولقطة منها |
| `payment_proof_path` | مسار صورة إثبات الدفع |
| `notes` | اختياري |
| `rejection_reason` | إلزامي عند الرفض |
| `approved_by`, `approved_at`, `rejected_by`, `rejected_at` | أثر المراجع |
| `club_subscription_id` | الاشتراك الحقيقي الناتج عن القبول، فريد لمنع التكرار |
| `created_at`, `updated_at` | التتبع الزمني |

لا يمكن تغيير طلب خرج من حالة `pending`. تمنع القيود والمعاملة الذرية اعتماد الطلب مرتين.

## واجهات API العامة

تضاف تحت `/api/public/portal`:

1. `GET /membership-plans` يعيد باقات الموقع المرتبطة والصالحة فقط، مع نوع الاشتراك الحالي (المعرف، الاسم، السعر، الأيام) ومحتوى العرض.
2. `GET /payment-methods` يعيد طرق الدفع المفعلة فقط من إعدادات طرق الدفع (`sales_pos_payment_methods.is_enabled = true`) وبحقول آمنة للعرض: المعرف، الاسم، الأيقونة، الوصف، وطريقة المحاسبة الأساسية. لا تعاد أي مفاتيح أو أسرار مزود دفع.
3. `POST /online-subscriptions` يستقبل `multipart/form-data`: `subscriptionTypeId`، `memberCode`، `customerName`، `startDate`، `paymentMethodId`، `paymentProof`، و`notes` اختيارياً.

الخدمة تتحقق من أن العضو موجود وأن الكود والاسم يطابقان سجله، وأن الباقة لا تزال نشطة ومتاحة لكل الفروع، وأن طريقة الدفع لا تزال نشطة، وأن صورة الدفع ملف صورة بالحجم والنوع المسموحين. تحسب النهاية من مدة نوع الاشتراك وتخزن جميع اللقطات السابقة قبل إعادة رسالة: «تم إرسال طلب الاشتراك بنجاح».

لا توجد واجهة رفع ملفات عامة منفصلة؛ الرفع جزء من إرسال الطلب فقط وبفئة مخصصة لصور إثبات دفع الاشتراكات.

## رحلة المستخدم في الموقع

1. تعرض صفحة العضوية الباقات القادمة من API فقط، وكل أزرارها تقول «اشترك الآن».
2. الضغط ينتقل إلى صفحة اشتراك جديدة مع معرف الباقة في الرابط. تعرض الصفحة تفاصيل الباقة الفعلية ثم طرق الدفع النشطة.
3. بعد اختيار طريقة الدفع والضغط على «تأكيد الاشتراك»، يظهر/ينتقل المستخدم إلى نموذج الطلب النهائي.
4. النموذج يطلب: صورة الدفع، كود العضو، اسم العميل، تاريخ بداية الاشتراك. الملاحظات اختيارية.
5. بعد نجاح الإرسال تظهر رسالة النجاح ولا يرسل النموذج مرة أخرى أثناء الطلب.

الواجهة العربية وRTL، وتعرض حالات التحميل والخطأ بوضوح. إذا لم توجد باقات مرتبطة، تعرض حالة فارغة صريحة بدلاً من بطاقات تجريبية.

## لوحة الإدارة

### إعداد باقة الموقع

توسع `GET /portal-management/options` بقائمة أنواع اشتراك النظام الصالحة. يتوسع نموذج باقات الموقع بحقل اختيار النوع، وتتحقق الخلفية منه عند الإنشاء والتعديل؛ لا يكفي تحقق الواجهة.

### اشتراكات الأونلاين

تضاف صفحة ومسار وصلاحية محميان بعنوان «اشتراكات الأونلاين». القائمة تعرض الأعمدة المطلوبة:

- كود العضو، الاسم، نوع الاشتراك، بداية ونهاية الاشتراك، الملاحظات، صورة الدفع، الحالة، والإجراء.

زر صورة الدفع يفتح الصورة في معاينة آمنة. للطلب المعلق زران:

- **قبول:** يعيد التحقق من العضو والباقة وطريقة الدفع، ثم داخل معاملة آمنة يستدعي مسار إنشاء الاشتراك المعتمد في `ClubSubscriptionsService` حتى ينشئ الاشتراك والإيصال والقيود المحاسبية بنفس قواعد النظام. يدفع بقيمة الباقة كاملة بطريقة الدفع المختارة، ويربط رقم الاشتراك الناتج بالطلب، ثم يغيّر الحالة إلى «تم اعتماد الاشتراك أونلاين».
- **رفض:** يفتح حقل سبب إلزامي. يحفظ السبب ويغير الحالة إلى «مرفوض» من دون إنشاء اشتراك.

أي فشل في إنشاء الاشتراك الحقيقي يلغي عملية القبول ولا يغير الطلب إلى مقبول. يعاد التحقق من صلاحيات الفرع للمراجع قبل الإجراء.

## الإشعارات

عند القبول ينشأ سجل في `am_member_notifications` للعضو بعنوان يفيد قبول طلب الاشتراك أونلاين، وبيانات تتضمن `onlineSubscriptionRequestId` و`clubSubscriptionId`.

عند الرفض ينشأ إشعار بعنوان يفيد رفض الطلب، وتتضمن البيانات والرسالة سبب الرفض. تستخدم التطبيق نفس قناة إشعارات الأعضاء الحالية؛ لا ترسل أسرار دفع أو صورة الإيصال في الإشعار.

## الأمان والاتساق

- لا يثق الخادم بالسعر أو الاسم أو المدة أو تاريخ النهاية القادم من المتصفح؛ يستخرجها ويحسبها خادمياً.
- لا تعرض واجهات الموقع نوع الاشتراك أو طريقة الدفع بعد تعطيلها.
- تفرض حدود الحجم ونوع الملف، ومسار رفع مستقل لصور إثبات الدفع، وفحص صلاحية الوصول قبل عرض الصورة في لوحة الإدارة.
- الاعتماد والرفض انتقالان أحاديان من `pending` فقط، مع تحديث شرطي داخل معاملة لمنع سباق المراجعين.
- يحتفظ الطلب بلقطات تاريخية حتى لا تتغير المراجعة عندما يعدل المدير السعر أو الاسم لاحقاً.

## الاختبارات والقبول

قبل التسليم تضاف اختبارات تغطي:

1. قائمة اختيار الباقات لا تعرض إلا الأنواع النشطة لكل الفروع وحفظ الرابط من شاشة البوابة.
2. API العام يرفض باقة أو طريقة دفع متوقفة، حقولاً إلزامية ناقصة، وصورة غير صالحة؛ ويحسب النهاية خادمياً.
3. الطلب الناجح يحفظ الصورة واللقطات والحالة `pending`.
4. القبول ينشئ اشتراكاً واحداً فقط، يربطه بالطلب، وينشئ الإشعار؛ والرفض يطلب السبب ولا ينشئ اشتراكاً وينشئ إشعاراً بالسبب.
5. بناء الموقع يعرض الباقات الديناميكية، وزر «اشترك الآن»، وصفحة الطلب وحالاتها.

معيار القبول النهائي: يستطيع المدير ربط باقة موقع بنوع اشتراك نشط لكل الفروع، ويرسل العضو طلباً كاملاً من الموقع، ثم يرى المدير بياناته وصورة الدفع ويقبله أو يرفضه، وتظهر نتيجة القبول في الاشتراكات الحالية ويصل إشعار العضو المناسب.
