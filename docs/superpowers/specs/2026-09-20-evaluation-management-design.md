# إدارة التقييمات — التصميم المعتمد

## الهدف والنطاق

إضافة نظام إدارة تقييمات مستقل عن وحدة التقييم القديمة الموجودة على المسار
`/hr/evaluations`. يحفظ النظام فئات تقييم مرتبطة بالمسميات الوظيفية، وبنوداً
لكل فئة، وتقييمات موظفين بفروعها وتفاصيل الدرجات. لا تعدّل هذه الإضافة جداول
أو API أو صفحة التقييمات القديمة.

يظهر النظام في قسم تنقل جديد باسم **إدارة التقييمات**، مباشرة بعد قسم إدارة
الموارد البشرية، ويحتوي على أربع صفحات: فئات التقييم، بنود التقييم، إضافة
تقييم، وتقرير التقييمات.

## تكامل المشروع وحدوده

- الخلفية NestJS وPrisma؛ الوحدة الجديدة في
  `backend/src/modules/evaluation-management/`.
- الواجهة React/Vite؛ الصفحات الجديدة في
  `frontend/src/pages/evaluation-management/`.
- المسمى الوظيفي المرجعي في المشروع هو `department_jobs` (وليس جدولاً باسم
  `job_titles`).
- الموظف المرجعي هو `employees`، والفرع المرجعي هو `tbl_branches`.
- مستخدم التدقيق المرجعي هو `users` ومفتاحه الأساسي `user_id`.
- لا يجري تعديل ملفات قائمة إلا لربط وحدة NestJS، إضافة مسارات React، وإدراج
  القسم في مصدر التنقل المركزي الحالي. لا يُعدل ملف الصفحة أو API القديمان.

## نموذج البيانات

ينشئ SQL/Prisma migration الجداول التالية باستخدام InnoDB. تكون المفاتيح
الخارجية حقيقية بين الجداول الجديدة فقط. أما المراجع إلى الجداول القديمة
`department_jobs` و`employees` و`tbl_branches` و`users` فتكون حقولاً مفهرسة
تتحقق الخدمة من وجودها وتوافقها قبل الحفظ، لأن بعض الجداول المصدر MyISAM ولا
يمكن لـ MySQL أن تكون هدفاً لمفتاح خارجي من InnoDB.

### `evaluation_categories`

- `id` مفتاح أساسي متزايد.
- `name` اسم الفئة، مطلوب.
- `job_title_id` مرجع مفهرس مطلوب إلى `department_jobs.id`.
- `created_at`, `updated_at` تاريخا ووقتا الإنشاء وآخر تعديل.
- `created_by_id`, `updated_by_id` مراجع مفهرسة قابلة لـ NULL إلى
  `users.user_id`؛ يسجلان المستخدم الذي أضاف أو عدّل الصف.
- قيد تفرد على `(name, job_title_id)` لمنع تكرار الفئة لنفس المسمى.

### `evaluation_items`

- `id` مفتاح أساسي متزايد.
- `category_id` مفتاح خارجي إلى `evaluation_categories.id`، مطلوب.
- `name` اسم البند، مطلوب.
- `max_score` رقم عشري غير سالب، مطلوب.
- حقول التدقيق نفسها: `created_at`, `updated_at`, `created_by_id`,
  `updated_by_id`.
- قيد تفرد على `(category_id, name)`.

### `employee_evaluations`

- `id` مفتاح أساسي متزايد.
- `category_id` مفتاح خارجي مطلوب إلى الفئة؛ و`employee_id` و`branch_id`
  مراجع مفهرسة مطلوبة إلى الموظف والفرع.
- `evaluation_date` تاريخ التقييم.
- `evaluation_month` قيمة شهر بتنسيق `YYYY-MM` لضمان حفظ الشهر كما اختاره
  المستخدم، حتى إن اختلف عن شهر التاريخ.
- حقول التدقيق نفسها في جميع الجداول.
- فهرس للتقرير على `(evaluation_date, category_id, employee_id)` وفهرس للفرع.

### `employee_evaluation_details`

- `id` مفتاح أساسي متزايد.
- `evaluation_id` مفتاح خارجي إلى `employee_evaluations.id`.
- `item_id` مفتاح خارجي إلى `evaluation_items.id`.
- `item_name_snapshot` و`max_score_snapshot` نسختان تاريخيتان من اسم البند
  ودرجته القصوى وقت الحفظ؛ يحافظان على صحة التقارير إذا عُدّل البند لاحقاً.
- `awarded_score` الدرجة الممنوحة، ضمن المجال من صفر إلى الدرجة القصوى.
- حقول التدقيق نفسها في جميع الجداول.
- قيد تفرد على `(evaluation_id, item_id)` لمنع تكرار البند داخل التقييم.

تُمنع إزالة فئة أو بند إذا كانت له تقييمات/تفاصيل مرتبطة. وتحفظ عملية إنشاء
التقييم الرئيسي وكل تفاصيله في Prisma transaction واحدة.

## API والصلاحيات

المسار الأساسي: `/evaluation-management`، تحت JwtAuthGuard. الصلاحيات تتبع
الموارد الأربعة المسجلة في كتالوج RBAC: `evaluation-management.categories`,
`evaluation-management.items`, `evaluation-management.add_evaluation` و
`evaluation-management.report`، مع أفعال `view/create/update/delete` المناسبة
لكل endpoint. لا تستخدم الوحدة مفتاح التقييم القديم `affairs.evaluations`.

- `GET /lookups/job-titles` و`GET /lookups/branches` endpoints داخل الوحدة
  لإرجاع المسميات والفروع بالصيغة التي تحتاجها الواجهة، ثم
  `GET/POST/PATCH/DELETE /categories` لإدارة الفئات.
- `GET/POST/PATCH/DELETE /items` لإدارة البنود.
- `GET /categories/:id/items` لإحضار بنود الفئة.
- `GET /categories/:id/employees?branchId=` لإحضار الموظفين الذين يطابق
  `mosma_wazefy_code` لديهم كود المسمى المرتبط بالفئة، مع تطبيق الفرع إن أُرسل.
- `POST /evaluations` لحفظ الرأس والتفاصيل atomically.
- `GET /evaluations` لتقرير مصفح يدعم `categoryId`, `employeeId`,
  `dateFrom`, `dateTo`.
- `GET /evaluations/:id` لتفاصيل modal كاملة.

أي إنشاء أو تعديل يملأ `created_by_id` أو `updated_by_id` من المستخدم المأخوذ
من JWT، ولا يثق بالقيم المرسلة من المتصفح. تتضمن DTOs التحقق من المعرفات،
التاريخ والشهر، عدم تكرار البنود، وعدم تجاوز `awardedScore` للحد الأقصى.

## الواجهة وتجربة الاستخدام

كل صفحة تعتمد مكونات الواجهة القائمة (`ListPageShell`, `DataTable`,
`Combobox`, `Dialog`, `react-query`) واتجاه RTL والترجمة الحاليين.

1. **فئات التقييم:** نموذج الاسم والمسمى، وجدول الاسم/المسمى/تعديل/حذف. يفتح
   التعديل داخل Dialog ويعرض الحذف تأكيداً.
2. **بنود التقييم:** نموذج الفئة والاسم والدرجة القصوى، وجدول الفئة/البند/الدرجة
   القصوى/الإجراءات، مع التحقق الفوري من الدرجة.
3. **إضافة تقييم:** اختيار الفئة والفرع والتاريخ والشهر؛ يؤدي اختيار الفئة إلى
   تحميل بنودها، ويؤدي اختيار الفئة أو الفرع إلى تحديث خيارات الموظف المطابق.
   لا يصبح زر الحفظ متاحاً إلا بعد اختيار موظف وإدخال درجة صالحة لكل بند.
4. **تقرير التقييمات:** مرشحات الفئة والموظف ومن/إلى تاريخ، وجدول التاريخ والشهر
   والفئة والموظف وزر التفاصيل. يعرض الزر Dialog يبين اسم كل بند والحد الأقصى
   والدرجة الممنوحة، مع معلومات التدقيق المتاحة.

يجري إبطال query cache المناسب بعد أي تغيير كي تتحدث القوائم مباشرة. تعرض
الشاشات رسائل الخطأ القياسية عبر `sonner`، وحالات التحميل/الفراغ الموجودة في
المشروع.

## التنقل والمسارات

تضاف مسارات الواجهة تحت `/evaluation-management/`:

- `/categories`
- `/items`
- `/add`
- `/report`

ويضاف قسم `evaluation-management` في `NAV_SECTIONS` بعد قسم HR، مع أيقونة من
`lucide-react` وبالمفاتيح الترجمية اللازمة. يستعمل المصدر المركزي للتنقل بدلاً
من تغيير JSX الخاص بالـSidebar، لأن الـSidebar الحالي يرسم القوائم منه.

## الاختبارات والتحقق

- اختبارات خدمة NestJS: CRUD، تصفية الموظفين بالمسمى والفرع، التحقق من الدرجات،
  transaction، منع الحذف المرتبط، وفلاتر التقرير.
- typecheck وbuild للـbackend والـfrontend.
- `prisma validate` للتأكد من صحة العلاقات.
- فحص يدوي موجز لمسارات الواجهة والتفاعل الديناميكي في البيئة المحلية.

- احتساب تقدير أو متوسط أو اعتماد سير موافقات؛ لم يطلب ضمن النطاق الحالي.
